# 01 · 产品概述与业务需求

> 本章让 AI 开发者理解「为什么做、为谁做、做到什么程度」。实现细节见后续章节。

---

## 1. 产品定位

**标书智能审核对比系统** 是面向 **沃泰能源海外储能投标专员** 的 **AI 原生标书竞标对比工具**，以「1 Orchestrator + 6 Agent」多 Agent 协作编排为核心能力，将海外大储招投标中的「拆解标书 → 提取技术参数 → 覆盖度核查 → 竞标对比 → 差距分级 → 修改建议」全流程自动化。产品首页为**对话式主页**（左侧导航 + 右侧对话框），作为统一入口进入项目工作台与竞标对比流程。

**产品形态**：单仓库双前端应用（`web-user` 用户端 + `web-admin` 管理端，共享 Node.js Express 后端 + MySQL）。

---

## 2. 业务背景

沃泰能源是面向全球的储能与智慧能源企业，产品覆盖户用储能、工商业储能、大型储能系统及 EMS、BMS 等核心部件，业务遍及欧洲等海外市场。海外大储项目主要通过招投标获得订单，需与 Tesla、BYD、CATL、Sungrow、Huawei 等国际对手同台竞争。

## 3. 建设目标（G1–G7，可验收）

| 编号 | 目标 | 验收口径 |
|:---:|------|---------|
| G1 | 标书拆解自动化 | 三件套上传后，Agent 自动完成结构化提取 |
| G2 | 覆盖度矩阵 | 每条硬性要求产出 ✅/❌/⚠️ |
| G3 | 差距清单 | 每条差距产出 🔴/🟡/🟢 三级分级 |
| G4 | 版本迭代闭环 | 版本时间线记录 V1→V2→V3… |
| G5 | 项目总报告 | 归档时自动汇总并支持 PDF 导出 |
| G6 | 全程可追溯 | 每次 Agent 运行输入/输出/耗时存档 |
| G7 | 对手标书归档与匹配 | 上传即归档；缺失时自动匹配推荐同类对标书 |
| G8 | 对话式主页入口 | 首页左侧导航 + 右侧对话框；MVP 仅「我的项目/新建项目/竞标对比」可交互，其余置灰 |

---

## 4. 业务价值

- 提效：数百页标书拆解对比从数天 → 分钟级。
- 提质：统一 Schema + 规则校验，消除人工漏项与口径不一致。
- 降本：提前暴露致命差距（缺认证、报价高），避免废标。
- 决策支撑：🔴🟡🟢 分级 + 修改建议，量化报价与方案。
- 知识沉淀：历史标书库 + 项目总报告沉淀为组织资产。
- 对标赋能：对手标书自动归档 + AI 匹配，无对手标书也能对标。

---

## 5. 适用边界（MVP）

**在范围内**：

- 储能招投标（户用 / 工商业 / 大型 / EMS+电池包）。
- 电子版 PDF（非扫描件），文本可被 pdf-parse 提取。
- 对话式主页（左导航 + 右对话框）：用户信息、功能模块、对话模块、项目模块、快捷按钮、标讯推荐（5 条写死）。
- 竞标对比（原 6 Agent 全流程，MVP 唯一可用的 AI 功能）。
- 投标专员全流程；Admin 独立管理端；技术负责人/法务/投标主管仅审批流体现（自动通过，本版不登录）。
- 对手标书自动归档 + 智能匹配推荐。

**不在范围内**（PPT 规划项）：

- 扫描件 OCR；三级审批独立页面；Agent 参数可视化配置；历史标书库管理端浏览界面；跨项目总报告；一键生成修改建议文档。
- 标讯追踪 / 招标解读 / 标书生成 / 标书审查（本版置灰，迭代实现）。
- 自由对话 / 对话记录 / 对话内文件上传 / 知识库（本版置灰或写死，不建 conversation/message 表）。
- 管理端「对话管理 / 知识库管理」模块（本版置灰，仅导航占位）。

## 6. 用户画像

### 6.1 角色总览

| 角色 | role 值 | 核心职责 | MVP 页面 |
|------|:---:|---------|---------|
| 投标专员 | `bidder` | 创建项目、上传文件（对手标书自动归档/缺失自动匹配）、触发 Agent、迭代、提交审批 | 用户端（web-user）：对话式主页 + 项目工作台全部页面 |
| 技术负责人 | `tech_lead` | 审核技术参数/可行性 | 审批流（自动通过，无页面，本版不登录） |
| 法务 | `legal` | 审核合同条款/商务风险 | 审批流（自动通过，无页面，本版不登录） |
| 投标主管 | `bid_director` | 最终终审 | 审批流（自动通过，无页面，本版不登录） |
| Admin | `admin` | 用户/角色/系统配置 | 管理端（web-admin）：系统仪表盘 + 用户管理 |

### 6.2 投标专员（核心用户）

- **特征**：熟悉储能技术与招投标；多对手并行；节奏快；人工对比工作量大易漏项。
- **诉求**：① 快速结构化拆解；② 自动核查硬性要求覆盖；③ 自动对比对手并给建议；④ 对手标书自动归档/缺失自动推荐；⑤ 多轮迭代可追溯；⑥ 一键出报告。
- **关键场景**：新建项目上传三件套 → 触发 Agent → 查看结果 → 修改 → 上传新版本 → 循环 → 提交审批 → 归档出报告。

### 6.3 Admin

- **诉求**：查看系统运行状态（项目数/Agent 运行次数/成功率/存储用量）、管理用户角色。
- **场景**：登录 → 系统仪表盘 → 用户管理。

## 7. 核心痛点（P1–P9）

| 编号 | 痛点 | 影响 | 解决方案 |
|:---:|------|------|---------|
| P1 | 人工拆解效率极低 | 交付周期长 | Agent1 + Agent2 |
| P2 | 参数对比易漏项 | 漏项致废标/报价偏差 | Agent2 Schema + Agent5 |
| P3 | 准确率难保证 | 对比不可信 | Agent3 规则+LLM + 统一 Schema |
| P4 | 差距无量化分级 | 修改不聚焦 | Agent5 + 🔴🟡🟢 |
| P5 | 硬性要求覆盖不明 | 漏满足硬性条款 | Agent1 + Agent4 |
| P6 | 版本无法追溯 | 汇报困难 | 版本时间线 + 版本 Diff |
| P7 | 知识无法沉淀 | 重复劳动 | 项目总报告 + 历史标书库 |
| P8 | 决策缺量化依据 | 决策慢 | 总报告图表 + PDF |
| P9 | 对手标书缺失/未沉淀 | 无法对标 | A8 归档 + A9 匹配 + Agent6 |

## 8. 业务主流程（单一操作闭环）

```
⓪ 登录进入对话式主页 → 通过「新建项目」或「我的项目/竞标对比」进入项目工作台
① 新建项目（项目信息 + 三件套）
   ├─ 上传对手标书 → 自动归档（建库/分类存储/元数据/索引）
   └─ 未上传对手标书 → 自动触发 Agent6 智能匹配 → 推荐对标书
② 触发 Agent 群（1→2→3→4→5，被采用对标书参与 2/5）
③ 查看结果（自审清单 + 覆盖矩阵 + 竞标差距 + 修改建议）
④ 修改标书 → 上传新版本（版本号 +1）→ 循环②③
⑤ 提交审批（仅当最新版本全部 Agent success）
⑥ 自动三级审批（技术✅→法务✅→主管✅，硬编码通过）
⑦ 归档 + 自动生成项目总报告 + 导出 PDF
```

## 9. 状态机

### 9.1 项目状态（projects.status）

```
draft → in_progress → awaiting_approval → approved → archived
                      （任意环节可 → rejected，MVP 简化）
```

| 状态 | 触发 |
|------|------|
| `draft` | 新建项目初始 |
| `in_progress` | 已上传文件 / 已触发 Agent |
| `awaiting_approval` | 点击「提交审批」 |
| `approved` | 三级审批通过 |
| `archived` | 点击「归档」（生成报告） |
| `rejected` | 驳回（MVP 保留状态，无页面） |

### 9.2 Agent 运行状态（agent_runs.status）

```
pending → running → success
                  ↘ failed → [重试] → pending → ...
```

### 9.3 审批流（自动三级）

```
提交审批 → 技术负责人(tech_lead) 自动通过 → 法务(legal) 自动通过 → 投标主管(bid_director) 自动通过 → approved
```
（每条 approval 记录 `decision=approved, auto_approved=1`）

## 10. 三条硬规则（必须实现）

| 规则 | 实现约束 |
|------|---------|
| **自审非强制** | Agent3 结果为「建议」，自审未通过仍可对比、可提交审批 |
| **AI 跑通才能提交审批** | 最新版本 5 个主流程 Agent 全部 `status=success`（Agent6 不纳入），否则「提交审批」按钮禁用 |
| **差距三级分级** | 所有差距项必须标注 `severity ∈ {red, yellow, green}` |

## 11. 版本管理规则（version_no）

- 项目版本以**我方标书**为核心驱动：创建时 `version_no=1`；点击「上传新版本」→ `version_no=当前最大+1`。
- `announcement`/`our_bid` 文件**跟随版本号**；`competitor_bid` 为**跨版本资产**（归档库不含版本号），其 `files.version_no` 仅记录归档时点，不参与版本隔离。
- `agent_runs`/`issues`/`approvals` 的 `version_no` = 本次分析针对的我方标书版本。
- 「上传新版本」可同时更新我方标书与招标公告；对手标书归档不触发版本递增。
