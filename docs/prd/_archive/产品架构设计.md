> **版本**：v1.0
> **日期**：2026-10-27
> **面向**：沃泰能源 AI 原生实践课题①落地

---

## 一、产品定位

**面向沃泰能源海外储能投标专员的 AI 原生标书审核对比工具**

**应用场景**：沃泰能源是面向全球的储能与智慧能源企业，产品覆盖户用储能、工商业储能、大型储能系统及 EMS、BMS 等核心部件，业务遍及欧洲等海外市场。海外大储项目主要通过招投标获得订单，一个项目需与 Tesla、BYD、CATL、Sungrow、Huawei 等多家国际对手同台竞争。

**核心解决的问题**：海外大储招投标中，标书动辄数百页，投标团队手动逐页拆解对手标书与招标参数、整理对比表、找出差距，既慢又容易漏项；储能产品涉及电池类型、循环寿命、逆变器效率、安全认证等大量技术参数，人工对比准确率和效率都很低，直接影响报价策略和中标率。

**一句话描述**：上传招标公告 + 我方标书 + 对手标书 → Agent 群自动拆解储能技术参数并对比 → 生成差距清单和修改建议 → 多轮迭代 → 审批归档 → 自动生成项目总报告。

## 二、用户角色

| 角色 | 核心职责 | MVP 实现状态 |
|------|---------|:-----------:|
| **投标专员** | 创建项目、上传文件、触发 Agent、修改迭代、提交审批 | ✅ 全实现 |
| **技术负责人** | 审核技术参数、方案可行性 | 📄 流程体现，页面不做 |
| **法务** | 审核合同条款、商务风险 | 📄 流程体现，页面不做 |
| **投标主管** | 最终决策终审 | 📄 流程体现，页面不做 |
| **Admin** | 用户/角色/系统配置 | 🔧 简化实现（硬编码角色） |

> **MVP 审批策略**：投标专员点击「提交审批」后，三级审批流（技术→法务→主管）在系统中硬编码为自动通过，不做独立审批页面。真实三级审批流程在 PPT 架构图中完整展示。

## 三、核心业务流程（MVP 版）

```
┌────────────────────────────────────────────────────────────────────┐
│  投标专员 · 单一操作闭环                                             │
├────────────────────────────────────────────────────────────────────┤
│                                                                    │
│  ① 新建项目                                                         │
│     ├── 填写：项目名称 / 招标方 / 投标截止日期 / 招标地区             │
│     ├── 储能场景分类：户用储能 / 工商业储能 / 大型储能 / EMS+电池包   │
│     └── 上传三件套：招标公告 + 我方标书 + 对手标书（可多份对手）        │
│                                                                    │
│  ② 触发 Agent 群工作流                                              │
│     ┌────────────────────────────────────────────────────┐         │
│     │  Agent Orchestrator（编排中心）                      │         │
│     │                                                     │         │
│     │  Agent1 招标公告解析                                │         │
│     │    ↓ 解析公告，提取硬性要求清单                       │         │
│     │  Agent2 文档解析                                    │         │
│     │    ↓ PDF → 我方/对手结构化字段                        │         │
│     │  Agent3 质量自审                                    │         │
│     │    ↓ 我方标书缺漏/重复/异常（非强制，仅建议）          │         │
│     │  Agent4 招标要求覆盖度                               │         │
│     │    ↓ 我方 vs 硬性要求，覆盖度矩阵                     │         │
│     │  Agent5 对手对比分析                                │         │
│     │    ↓ 我方 vs 对手，差距清单 + 🔴🟡🟢 分级             │         │
│     └────────────────────────────────────────────────────┘         │
│                          ↓                                          │
│     输出 → 自审清单 + 招标覆盖矩阵 + 对手差距表 + 修改建议            │
│                                                                    │
│  ③ 查看结果 → 修改标书 → 上传新版本                                  │
│     （自审未通过也可继续，AI 自审是建议不是硬门槛）                    │
│                                                                    │
│     循环 ②③ 直到满意                                                 │
│                                                                    │
│  ④ 提交审批                                                         │
│     （AI 自审 + 对比均跑通后才可用此按钮）                             │
│                          ↓                                          │
│     ┌─────────────────────────────┐                                 │
│     │  自动三级审批（硬编码通过）   │                                 │
│     │  技术负责人 ✅  →  法务 ✅    │                                 │
│     │       →  投标主管 ✅          │                                 │
│     └─────────────────────────────┘                                 │
│                          ↓                                          │
│  ⑤ 归档 + 自动生成项目总报告                                         │
│     ├── 版本迭代时间线（V1→V2→V3...）                                │
│     ├── 每个版本的 AI 自审问题数 + 差距问题数                         │
│     ├── 版本修改次数 / 总耗时                                        │
│     ├── 问题分类统计（自审 vs 招标差距 vs 对手差距）                  │
│     └── 可导出 PDF                                                  │
│                                                                    │
└────────────────────────────────────────────────────────────────────┘
```

### 三条硬规则

| 规则 | 说明 |
|------|------|
| **自审非强制** | Agent3 质量自审的结果是"建议"而非"硬门槛"。自审未通过，专员仍可进入对比环节或提交审批。 |
| **AI 跑通才能提交审批** | 最新版本必须经过完整 Agent 工作流且所有 Agent 执行成功，「提交审批」按钮才可用。 |
| **差距三级分级** | 所有差距项必须标注 🔴致命 / 🟡重要 / 🟢次要，帮助专员 prioritize 修改。 |

## 六、Agent 群架构（5 Agent + 1 编排中心）

```
┌───────────────────────────────────────────────────────────────┐
│                    Agent Orchestrator                           │
│       调度 5 个 Agent 依次执行 · 汇总结果 · 给前端汇报状态        │
│       · 失败自动重试 · 输出统一存入 PostgreSQL issues 表          │
└───┬──────────┬──────────┬──────────┬──────────┬───────────────┘
    │          │          │          │          │
    ▼          ▼          ▼          ▼          ▼
 ┌──────┐  ┌──────┐  ┌──────┐  ┌──────┐  ┌──────┐
 │Agent1│  │Agent2│  │Agent3│  │Agent4│  │Agent5│
 │招标  │  │文档  │  │质量  │  │招标  │  │对手  │
 │公告  │  │解析  │  │自审  │  │要求  │  │对比  │
 │解析  │  │      │  │      │  │覆盖  │  │分析  │
 └──┬───┘  └──┬───┘  └──┬───┘  └──┬───┘  └──┬───┘
    │         │         │         │         │
    ▼         ▼         ▼         ▼         ▼
 招标公告    我方+对手   我方标书   我方 vs   我方 vs
 PDF→     PDF→结构化   缺漏/重复   招标要求   对手标书
 硬性要求   字段 JSON    异常值     覆盖矩阵   差距清单
 清单 JSON  各一份      +修改建议   ✅❌⚠️    🔴🟡🟢
```

### 各 Agent 职责明细

#### Agent1 招标公告解析

| 项目 | 说明 |
|------|------|
| **输入** | 招标公告 PDF 文本 |
| **输出 JSON** | `{requirements: [{category, item, is_mandatory, source_page}]}` |
| **核心逻辑** | ① PDF 文本提取（pdfplumber / PyMuPDF）<br>② LLM 识别硬性要求，按分类整理 |
| **分类** | 资质要求 / 技术参数要求 / 商务条款 / 截止日期 |
| **储能典型要求** | 电池类型（LFP 强制）/ 循环寿命 ≥ 6000 次 / 逆变器效率 ≥ 97.5% / IEC 62619 安全认证 / CE 认证 / VDE-AR-N 4105 并网标准 / 质保 ≥ 10 年 |
| **LLM 调用** | System Prompt 引导 LLM 从公告中提取储能硬性条款并结构化输出 |

#### Agent2 文档解析

| 项目 | 说明 |
|------|------|
| **输入** | 我方标书 PDF + 对手标书 PDF（各一份） |
| **输出 JSON** | 每家公司一份：`{company_name, technical_params: {...}, commercial_terms: {...}, qualifications: {...}, pricing: {...}}` |
| **核心逻辑** | ① 分别提取两家 PDF 文本<br>② LLM 按统一 schema 映射字段 |
| **Schema** | technical_params（技术参数）/ commercial_terms（商务条款）/ qualifications（资质）/ pricing（报价） |
| **储能技术参数 schema** | `{`<br>`  battery_type: "LFP/NMC",`<br>`  rated_capacity_kwh: 1000,`<br>`  rated_power_kw: 500,`<br>`  storage_duration_h: 2,`<br>`  cycle_life: 6000,`<br>`  inverter_efficiency: 97.5,`<br>`  system_efficiency: 90,`<br>`  energy_density_whl: 250,`<br>`  dod: 95,`<br>`  warranty_years: 10,`<br>`  certifications: ["IEC 62619", "UN38.3", "CE", "VDE-AR-N 4105"],`<br>`  ems_integrated: true,`<br>`  bms_type: "主动均衡",`<br>`  install_type: "户用/工商业/大型地面",`<br>`  grid_mode: "并网/离网/混合"`<br>`}` |

#### Agent3 质量自审

| 项目 | 说明 |
|------|------|
| **输入** | Agent2 我方 JSON |
| **输出 JSON** | `{issues: [{type, field, current_value, severity, suggestion}]}` |
| **核心逻辑** | ① 规则校验（必填字段是否为空、数值是否在合理范围）<br>② LLM 判断字段合理性（报价是否异常低、技术参数是否遗漏） |
| **type** | missing（缺失）/ duplicate（重复）/ abnormal（异常值） |
| **储能校验规则示例** | ① 循环寿命必须 ≥ 3000 次才合理<br>② 逆变器效率应在 95%-99% 之间<br>③ CE/IEC 认证对欧洲市场是必填<br>④ 报价低于 0.1 欧元/Wh 可能异常 |
| **⚠️ 非强制** | 自审结果是建议，不是提交审批的硬门槛 |

#### Agent4 招标要求覆盖度

| 项目 | 说明 |
|------|------|
| **输入** | Agent1 硬性要求清单 + Agent2 我方 JSON |
| **输出 JSON** | `{coverage: [{req_item, category, our_status, evidence}]}` |
| **核心逻辑** | ① 逐字段匹配<br>② LLM 语义判断覆盖度 |
| **our_status** | ✅ covered（已覆盖）/ ❌ missing（缺失）/ ⚠️ not_met（不满足） |
| **储能示例** | 招标要求"循环寿命 ≥ 6000 次" → 我方标书写 5500 次 → ⚠️ not_met |

#### Agent5 对手对比分析

| 项目 | 说明 |
|------|------|
| **输入** | Agent2 我方 JSON + Agent2 对手 JSON |
| **输出 JSON** | `{gaps: [{field, category, our_value, opponent_value, severity, gap_description, suggestion}]}` |
| **核心逻辑** | ① 逐字段 diff<br>② LLM 业务推理差距严重度分级 |
| **severity** | 🔴 red（致命差距：如缺少 CE 认证、循环寿命低 30%+、报价高 20%+）<br>🟡 yellow（重要差距：如逆变器效率低 1%、质保少 2 年）<br>🟢 green（次要差距：如安装方式描述略差） |
| **储能对比示例** | 我方循环寿命 5000 次 vs 对手 Tesla Megapack 7000 次 → 🔴 致命差距，建议改用高循环电芯 |

## 七、数据模型（PostgreSQL）

```sql
-- 用户表
users
├── id              UUID 主键
├── name            VARCHAR(100) 姓名
├── password_hash   VARCHAR(255) 密码
├── role            VARCHAR(50) 角色：bidder / tech_lead / legal / bid_director / admin
├── department      VARCHAR(100) 部门
├── created_at      TIMESTAMP
└── updated_at      TIMESTAMP

-- 项目表
projects
├── id              UUID 主键
├── name            VARCHAR(200) 项目名称
├── bidder          VARCHAR(200) 招标方名称
├── deadline        DATE 投标截止日期
├── region          VARCHAR(100) 招标地区（如：德国/荷兰/西班牙/中国）
├── storage_type    VARCHAR(50) 储能场景：residential / commercial / utility / ems_battery
├── description     TEXT 项目描述
├── status          VARCHAR(30) 状态：draft / in_progress / awaiting_approval / approved / archived / rejected
├── creator_id      UUID → users.id
├── created_at      TIMESTAMP
└── updated_at      TIMESTAMP

-- 文件表
files
├── id              UUID 主键
├── project_id      UUID → projects.id
├── version_no      INTEGER 版本号（V1=1, V2=2...）
├── file_type       VARCHAR(30)：announcement / our_bid / competitor_bid
├── original_name   VARCHAR(255) 原始文件名
├── minio_path      VARCHAR(500) MinIO 存储路径
├── minio_url       VARCHAR(500) 访问 URL
├── file_size       BIGINT 文件大小（字节）
├── uploader_id     UUID → users.id
├── created_at      TIMESTAMP

-- Agent 运行记录
agent_runs
├── id              UUID 主键
├── project_id      UUID → projects.id
├── version_no      INTEGER
├── agent_name      VARCHAR(50)：parse_announcement / parse_document / quality_check / requirement_coverage / competitor_compare
├── status          VARCHAR(30)：pending / running / success / failed
├── input_json      JSONB Agent 输入完整存档
```

## 十、风险与兜底方案

| 风险 | 发生概率 | 兜底方案 |
|------|:--------:|---------|
| Agent 实时调 LLM 出错/太慢 | 高 | **提前生成 mock 数据**：3 份模拟标书 PDF + 预先生成好 Agent 输出 JSON，万一实时调不通直接读 JSON |
| PDF 扫描件无法提取文本 | 中 | mock 标书全部用电子 PDF（非扫描件），PPT 说明生产环境扩展 OCR |
| 前端 API 联调卡住 | 中 | 先用 hardcode mock 数据展示 UI，截图不受影响 |
| Docker 镜像拉取网络卡壳 | 低 | 提前启动 Docker 拉镜像，或用本地已有镜像 |
| 某个 P0 页面做不完 | 低 | 用 Ant Design 现成组件，不自定义样式 |
